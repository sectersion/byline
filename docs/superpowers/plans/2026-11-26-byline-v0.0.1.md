# byline v0.0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local daemon that accepts WakaTime heartbeats, stores them raw in sqlite, forwards them upstream transparently, and reports hours per project per day.

**Architecture:** One sync process. Std TcpListener or tiny_http serving four endpoints on 127.0.0.1; every heartbeat written to sqlite exactly as received before any network activity; a forwarding pass drains `where forwarded_at is null` with backoff. Derivation (report/status) is pure functions over the heartbeats table.

**Tech Stack:** Rust, sqlite (rusqlite, bundled), one sync HTTP listener, serde_json, ureq (TLS) for forwarding.

**Spec:** Briefing "byline v0.0.1" (pasted, 2026-11-26) + CLAUDE.md. Note: the spec references CURRENT.md, docs/schema.sql, docs/event.md as existing — they do not. Task 0 creates them.

## Global Constraints

- One process, one sqlite file, one input, one output.
- No file over 400 lines; warn at 300. `src/` total under 2,500 lines.
- Max 1 new dependency per PR, added to ALLOWED in budget_test.rs same commit.
- No new top-level directory, no second crate, no second route/page/HTML.
- Never store prompts, code, file contents, keystrokes, window titles — including logs and errors.
- Never cache a derived number in a column.
- Never poll the filesystem; signals are pushes only.
- Every change: 1 issue + 1 PR, never merge to main directly.
- Bind 127.0.0.1 only.

## Open Questions — STOP AND ASK before Task 1 merges

1. **The six tables.** docs/schema.sql doesn't exist; the schema is declared frozen but is unwritten. Proposed draft (needs Oliver's sign-off before Task 0 commits it, because after that it never changes):
   - `heartbeats` (id, raw_payload, received_at, forwarded_at, auth_method)
   - `unknown_paths` (id, path, method, hit_at)
   - `auth_keys` (id, key_hash, label) — or is the key single-user config?
   - `meta` (schema_version) — or does user_version cover it?
   - …plus 2 more. **What are the other tables for v0.0.1?** If the honest answer is "two," the answer is two tables and a smaller number — the count shouldn't be reverse-engineered.
2. **HTTP stack:** hand-rolled on `std::net::TcpListener` (zero deps, but must survive real plugin clients — chunked encoding, keep-alive, 100-continue) vs `tiny_http` (one small sync crate, handles those). Ponytail says tiny_http; recommend it.
3. **Forwarding TLS:** `ureq` with rustls. Confirms one dep for that PR.
4. **Auth model:** the spec accepts any Basic key — is there actually a key check, or does byline accept anything and pass it through? Spec reads as pass-through; confirm.

### Task 3: Forwarding — the transparent proxy

**Files:**
- Create: `ingest/forward.rs`
- Modify: `ingest/server.rs` (kick a forward pass after successful local write)

**Interfaces:**
- Consumes: heartbeats table.
- Produces: `ingest::forward::drain(store: &Store) -> usize` — posts each unforwarded row's original body to the original api_url with the original key; sets forwarded_at on 2xx; backoff on failure; never blocks or fails the local write.

- [ ] Step 1: Failing test — with a local stub upstream, forwarded rows get forwarded_at set; with upstream down, rows stay queued and the local write still succeeds; restart resumes without double-forwarding committed rows (idempotence check on `forwarded_at is null`).
- [ ] Step 2: Implement drain with capped exponential backoff. Retry queue is the query, not a table.
- [ ] Step 3: Test green, commit, PR. Dep this PR: `ureq`.
